risk-sentinel / dev-sec-ops-baseline

Pipeline Evidence Plane

Extending the DevSecOps baseline from “a scan artifact landed on the runner” to “the platform’s security control plane is configured, enabled, and producing evidence” — as one profile that runs both standalone and inside the sparc-validate orchestration.

2026-08-14 main @ a34a100 14 controls today 21 repos in scope

Why this work

dev-sec-ops-baseline holds 14 input-gated controls that assert a pipeline scan ran and emitted a well-formed file. Every one of them resolves to file(ArtifactHelper.path(adir, …)) against a local reports/ directory. That makes the profile in-pipeline only: it must execute on the runner, after the scanners, with artifacts already on disk. It has no overlay in sparc-validate, no CI leg, and has never been exec’d against a real pipeline.

Measured against the ten DevSecOps practices we’re targeting, artifact-presence covers one and a half of them. The rest — shift-left enforcement, merge gating, policy-as-code, secure-coding evidence, vulnerability-dashboard monitoring, threat modeling — are control-plane facts held by GitHub and GitLab, not files on a runner. Roughly two-thirds of the target surface is unreachable from the filesystem.

What we’re building on, not building

Three pieces of existing machinery carry most of this. None of them needs to be invented.

The fetch resource pattern

sparc-validate/tools/attestation/document_attestation.rb already speaks github://, gitlab://, s3://, https:// and file://, with token resolution from opts→ENV and — critically — a connection_error path so an unreachable source fails instead of quietly passing. Its initialize(uri = nil, opts = {}) shape also encodes the Ruby 3 positional-opts lesson. The new resources clone this pattern rather than re-deriving it.

The HDF conversion path

The org already runs hdf fetch / hdf convert in production. container-build-sign/.github/workflows/sonarqube-hdf.yml does hdf fetch sonarqube → OHDF → S3 evidence bucket and is called from four repos; sca-emit-images.yml uses --from grype; build-sign-publish.yml uses --from sarif. GitHub code-scanning alerts are retrievable as SARIF, so the dashboard→HDF bridge is an existing converter plus a fetch — no new converter.

The KSI system of record

risk-sentinel/sparc seeds an 11-theme FedRAMP 20x KSI catalog (db/seeds/fedramp_20x_ksi.rb) plus a ControlMapping to NIST 800-53r5, served read-only at /api/v1/ksi_catalog/{themes,indicators,mappings}, with /api/v1/…/ksi_validations for write-back. The profile consumes this. It does not fork a KSI table into PROVENANCE.md.

Two run modes, and why order matters

The profile has to satisfy two callers with different prerequisites. Conflating them is how you get a control that silently passes because its input was never populated.

Ordering is a correctness property, not a convenience

  • Enablement precedes findings. “Is Code Security on?” must be evaluated before “how many open alerts?” — otherwise a disabled repo reports zero alerts and looks clean.
  • Production precedes validation. The SBOM-validity control is meaningless before the SBOM control; Grype consumes the SBOM Syft produced.
  • Do not rely on InSpec execution order to express this. InSpec gives no cross-file ordering guarantee. Each dependent control encodes its precondition explicitly in its own body — a resource-level predicate, not a hope about file sequence.
  • Mode selection is an input, not an inference. A single run_mode input (pipeline / control-plane / both) gates the families. Absent artifacts must not be indistinguishable from “this mode doesn’t check artifacts.”

The measurement that shapes phase one

I probed the GitHub security APIs directly against the org. Code Security is off on most private repos:

sparc-validate   code-scanning   → 403  "Code Security must be enabled"
                 dependabot      → 403  "Dependabot alerts are disabled"
                 secret-scanning → 404  "Secret scanning is disabled"
sparc-iac        → same three
sparc            → all three respond (public repo — free tier)
cis-*-baseline   → all respond, 0 alerts (public, free tier)

A naive resource reads 403 as an empty alert list and passes. That is exactly the silence-as-success defect class that produced every serious bug in this stack in August: a step that assessed nothing while reporting not-red.

So the first control written is the enablement control, and 403/404 map to FAIL with the API message carried into the result. “Code Security is not enabled on this repository” is a genuine, actionable finding — arguably the most valuable one in the set, and the thing that drives the licensing decision rather than waiting on it.

Correction: every responding repository above is public

An earlier reading of this probe treated sparc as proof that Code Security is switched on somewhere. It is not — sparc is a public repository, where code scanning and secret scanning are free. That splits the remediation into two different asks with two different owners: on private repositories Dependabot alerts are a free toggle, while code scanning and secret scanning need paid Code Security licensing. A plan that treats all three as one switch stalls on the wrong blocker.

Four surfaces, not two

The coverage table above splits the world into “files on a runner” and “control plane”. Building phase 1 showed that collapses genuinely different things, and the distinction decides whether a given check can run at all. Phase 1.5 added a fourth.

The fourth surface is what makes a standalone sweep useful

A tool with no API cannot be seen from outside its pipeline. TruffleHog is the standing case, and before this surface existed a control-plane sweep reported “enabled but not reachable from this run mode” for most of the estate — accurate, and not much use.

Reading the converted HDF out of the evidence bucket closes that: coverage in control-plane mode went from 20 satisfied cells to 44. It is also the surface that only exists because the conversion sweep put the evidence there in the first place.

Credential failures raise rather than fail. A missing AWS credential says nothing about whether a scan ran; failing would assert something untrue and skipping would read as not-applicable. The exception makes InSpec emit failed-with-backtrace, which Heimdall renders as Profile Error — no credit, and visibly not an assessment. That is deliberately inconsistent with the other resources, which capture and fail.

Where merge-request rules actually live

They straddle the boundary, which is why the third surface has to exist. Whether reviews are required is platform state a token reads from the protection endpoint. Whether the security scan fires on a merge request at all is a fact about a YAML file, and no security endpoint reports it. A repository can require status checks that include no security scan — strong on the API surface, hollow in practice. Reading one surface would miss it entirely.

There is no “not declared” state

Every scan type is declared for every repository, enabled: true or enabled: false. Omission would render as Not Applicable in HDF, which reads as “does not apply here” rather than “nobody has looked” — a false maturity signal in an assessment. An explicit enabled: false yields a skip carrying “must be manually verified and attested to”, which the attestation flow can satisfy with a signed rationale.

A scan declared enabled that the profile cannot yet see yields a differently worded skip. That gap belongs to us, not to the repository, and an attestation must not paper over it. The two skips stay verbally distinct so they remain distinguishable in HDF.

The denominator cannot come from the file being verified

If the target list were both the claim and the scope, a repository nobody added would be invisible — the same failure mode one layer up. Reconciliation enumerates the organisation through the forge API and fails on undeclared repositories, stale declarations, and exclusions carrying no written reason. Archived, fork and template repositories are not auto-excluded: churn in the input file is the intended cost of never silently shrinking the denominator.

Two vocabulary collisions are settled once in the registry rather than left to drift: dependency resolves to sca (GitLab’s name for the same concern), and container is separated from sca by the target rather than the tool, since Grype and Trivy serve both. iast is carried as a scan type with no tools attached — no tooling anywhere in the organisation performs it, and an absent row would imply the concept does not apply rather than that nobody does it.

Build sequence

Numbered because it is a real dependency chain — each phase consumes the one before it. Every phase is one issue, one branch, one PR, per issue_rules.md.

01

Resource, capability matrix, and coverage docs

dev-sec-ops-baseline · four coupled parts

Scoped to the resource alone at first, then widened: a fetch mechanism with no capability-declaration model gives users nothing to configure and a README that describes nothing. The phase delivers the resource, the registry, the declaration schema, and generated documentation of reach — one logical unit.

Clone the document_attestation shape: initialize(repo = nil, opts = {}), token from opts[:token] → ENV, all network failure captured in connection_error. Exposes code_security_enabled?, secret_scanning_enabled?, dependabot_enabled?, branch_protection(branch), rulesets, workflow_triggers(path), open_alerts(kind). Every predicate raises-or-fails on a transport error; none of them returns a falsy default that masks an unreachable API.

Constraint carried in: InSpec resources cannot call input(). Tokens and repo names arrive through the opts hash, passed from the control body. defined?(input) is not a usable guard.

02

Enablement controls

controls/platform_enablement.rb

One control per capability — code scanning, secret scanning with push protection, Dependabot alerts and security updates. These are the preconditions everything downstream depends on, and they are the phase that produces immediate, real findings against the current org state. Anchor to RA-5, SI-5, SA-11; the KSI rollup follows in phase 6.

03

Practice controls on the control plane

controls/pipeline_governance.rb

The six practices that are unreachable from the filesystem: required status checks and required reviews (delivery gating), rulesets and their enforcement status (policy as code), scan-workflow trigger analysis (shift left — does the scanner fire on pull_request, or only after merge?), CODEOWNERS coverage (shared responsibility), signed-commit requirement, and stale-review dismissal.

04

Dual-mode packaging

dev-sec-ops-baseline + sparc-validate/overlays/

Introduce run_mode and gate the two families. Add inputs/control-plane.yml alongside the existing pipeline input files. Create overlays/dev-sec-ops/ in sparc-validate following the established overlay shape — depends: on a tagged upstream, controls/include.rb, an inputs.yml carrying the 20-repo list, and the --input-file wiring on the exec leg. Remember that repeated --input flags are silently dropped; one flag with many pairs, or a second input file.

This is the phase that first exec-validates the profile. Static check and json only load controls — they have never proven a single one of these 14 assertions runs.

05

Dashboard → HDF bridge

container-build-sign reusable

Fetch code-scanning alerts as SARIF and run them through the existing hdf convert --from sarif, emitting to the same S3 evidence bucket the SonarQube path already writes to. Follows the sonarqube-hdf.yml reusable-workflow pattern exactly, so the vulnerability dashboard joins the unified evidence stream Heimdall already aggregates rather than becoming a parallel one.

Dependabot and secret-scanning alerts have no SARIF form and no stock converter — handle them as a separate decision, not a silent omission.

06

KSI wiring through SPARC

sparc API · not a local table

The profile keeps emitting tag nist: and SPARC resolves coverage through its existing mapping. A generator pulls /api/v1/ksi_catalog/mappings and stamps a derived tag ksi: into the profile so the value is pinned and reviewable in a PR — derived from the system of record, never hand-maintained beside it.

07

GitLab portability

fixture-tested, not exec-validated

Build gitlab_security to the same interface against the vulnerability-report and security-policy APIs, validated against a recorded fixture. All 20 org repos are on GitHub today and there is no live GitLab instance, so this ships explicitly labelled as portability-only. No exec-validation claim.

Decisions worth flagging before we start

KSI mapping direction is not reversible

SPARC’s mapping is typed superset — “each KSI encapsulates the intent of multiple NIST controls” (ksi-cm-04 → sa-11, ksi-cna-02 → cp-6, cp-7). Reverse-resolving NIST→KSI is therefore necessary but not sufficient: a passing SA-11-tagged control does not on its own satisfy ksi-cm-04. The profile must not assert KSI status. It emits NIST tags; SPARC decides coverage from the full set.

SPARC’s KSI catalog looks like an earlier 20x release

The seeded themes are AUTH · CM · CNA · EDU · IAM · IR · MLA · POL · REC · SVC · SCR. Current FedRAMP 20x publications use a partly different set of theme codes and drop the authorization theme. That drift belongs in a sparc issue against the seed, pinned to a specific FRMR release — it should not be papered over or forked into this profile.

The profile has never been exec’d

Zero of the 14 controls has run against a real pipeline. check and json load controls; they do not evaluate them. Phase 4 is where that debt gets paid, and the plan deliberately places it before the dashboard and KSI work rather than after.

How each phase is proven

  • Resource behaviour (1): exercise github_security against a repo with Code Security on (sparc), one with it off (sparc-validate), and an unreachable host. The off case must FAIL with the API message; the unreachable case must FAIL, not pass empty.
  • Static gates (1–3): vendor → check → json in the pinned sparc-auditor image. The json leg is non-optional — it catches library load errors check does not.
  • Live exec (2–4): exec -t local:// --input-file inputs/control-plane.yml across all 20 repos, then read the HDF. Every control must land on pass or fail with a reason; a run where controls skip silently is a failed verification, not a clean one.
  • Bolt-on mode (4): run the profile as the last step of one real pipeline with reports/ populated, and confirm the artifact family evaluates rather than skips.
  • Evidence stream (5): confirm the converted SARIF lands in the S3 evidence bucket under the same layout the SonarQube emit uses, and renders in Heimdall.

Scope confirmed: all 21 risk-sentinel repositories · GitLab portability-only · Code Security assumed to be enabled on the private repos, with the enablement failures driving that change rather than blocking on it.

Every phase follows the 13-step workflow in docs/dev/issue_rules.md: issue first, branch prefixed with the issue number, no direct pushes to main, no self-merges.
