# KSI coverage

Which FedRAMP Key Security Indicators this profile's controls reach, and which
they do not.

---

## Where the mapping comes from

[`files/ksi_mapping.yml`](../files/ksi_mapping.yml), transcribed from the
**FedRAMP Consolidated Rules for 2026** — the authoritative machine-readable
publication. It is committed rather than fetched: reading it from a running
SPARC instance would make this profile unrunnable by anyone who does not have
one, and every profile repository in this estate is clone-to-results.

The published mapping runs KSI → NIST. This profile tags NIST, so it needs the
reverse. [`tools/ksi_resolver.py`](../tools/ksi_resolver.py) builds that index
and classifies each link; the renderers write the result into the control files
as literals, because InSpec reads tag values from the AST at parse time and
raises on anything computed.

## What the tags mean

| Tag | Claim |
|---|---|
| `ksi` | The link holds. Either the indicator cites this control, or it cites the base of an enhancement we tag. |
| `ksi_broader` | We tag the **base** of an enhancement the indicator cites — `SA-15` against an indicator citing `sa-15.3`. Satisfying the base says nothing about that enhancement, so this is named and not asserted. |
| `ksi_unmapped` | No indicator cites this control or any enhancement of it. Recorded so that "we looked and there is no path" cannot be read as "nobody ran the generator". |

`ksi` is emitted on every control, empty if need be. Its presence is the proof
the generator visited that control at all.

## What this profile does not claim

It does not decide that a KSI is **satisfied**. Each indicator encapsulates the
intent of several NIST controls, so reverse resolution is necessary and not
sufficient — evidence from parts of the boundary this profile never sees is also
required. The rollup belongs to the consuming system.

Reaching 0 of 4 on Recovery Planning is therefore the correct answer, not a gap
to close here. A pipeline-evidence profile has nothing to say about backup
restoration, and tagging it as though it did would be the more damaging error.

## Not filtered to a baseline

Nothing here is pruned to what resolves against the FedRAMP High resolved
catalog this estate publishes. [dev-sec-ops-baseline#40][40] is open on that
question and under peer review; this wiring deliberately does not depend on its
outcome.

[40]: https://github.com/risk-sentinel/dev-sec-ops-baseline/issues/40

## Refreshing

When FedRAMP publishes a new release, re-transcribe `files/ksi_mapping.yml` from
the source named in its header, then:

```bash
python3 tools/render_ksi.py        # rewrites tags and this document
python3 tools/render_controls.py   # coverage.rb gets its tags from the same resolver
python3 tests/ksi_resolver_test.py
```

CI runs both renderers with `--check`, so a refresh that forgets to re-render
fails rather than shipping a document that describes the previous release.
